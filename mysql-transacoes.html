Preparação do banco de dados

Execute os comandos em uma conexão MySQL de testes, na ordem apresentada. Use um banco novo e vazio; não execute em produção.

1. Criar o banco e a tabela

CREATE DATABASE IF NOT EXISTS laboratorio_transacoes
    CHARACTER SET utf8mb4;
USE laboratorio_transacoes;

CREATE TABLE contas (
    id INT PRIMARY KEY AUTO_INCREMENT,
    titular VARCHAR(100) NOT NULL,
    saldo DECIMAL(12,2) NOT NULL DEFAULT 0,
    CONSTRAINT chk_saldo CHECK (saldo >= 0)
) ENGINE = InnoDB;

DECIMAL preserva a precisão monetária. CHECK impede saldo negativo nas versões indicadas. InnoDB permite transações.

2. Inserir dados iniciais

INSERT INTO contas (id, titular, saldo) VALUES
    (1, 'Ana', 1000.00),
    (2, 'Bruno', 500.00),
    (3, 'Carla', 750.00);

3. Conferir os dados

SELECT * FROM contas ORDER BY id;
SELECT SUM(saldo) AS total FROM contas;

4. Restaurar dados entre exercícios

Use apenas no banco de testes, depois de encerrar qualquer transação em todas as sessões. Os exemplos assumem que as três contas existem.

ROLLBACK;
SET autocommit = 1;
UPDATE contas SET saldo = CASE id
    WHEN 1 THEN 1000.00
    WHEN 2 THEN 500.00
    WHEN 3 THEN 750.00
END WHERE id IN (1, 2, 3);

Primeiras transações em SQL

A. Confirmar uma transferência

START TRANSACTION;
UPDATE contas SET saldo = saldo - 200 WHERE id = 1;
UPDATE contas SET saldo = saldo + 200 WHERE id = 2;
COMMIT;
SELECT * FROM contas ORDER BY id;

Resultado a partir dos dados originais: Ana = 800, Bruno = 700, Carla = 750.

B. Cancelar uma transferência

START TRANSACTION;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
ROLLBACK;
SELECT * FROM contas ORDER BY id;

Se executado depois de A, os saldos permanecem 800, 700 e 750. Se restaurados antes, permanecem 1000, 500 e 750.

C. INSERT e DELETE também são transacionais

START TRANSACTION;
INSERT INTO contas (titular, saldo) VALUES ('Diego', 100);
DELETE FROM contas WHERE id = 3;
SELECT * FROM contas;
ROLLBACK;
SELECT * FROM contas;

Diego desaparece e Carla reaparece após o rollback. O contador AUTO_INCREMENT pode apresentar lacunas.

Esses exemplos supõem que os comandos sejam bem-sucedidos. Uma transação não impede por si só que a aplicação confirme uma transferência incompleta: confira erros e linhas afetadas antes de COMMIT.

SAVEPOINT · Recuperação parcial

Como um ponto de recuperação em um jogo: volte a um estado intermediário sem cancelar tudo.

START TRANSACTION;
UPDATE contas SET saldo = saldo + 100 WHERE id = 1;
SAVEPOINT ponto1;
UPDATE contas SET saldo = saldo - 50 WHERE id = 2;
UPDATE contas SET saldo = saldo + 300 WHERE id = 3;
ROLLBACK TO SAVEPOINT ponto1;
COMMIT;

Com os dados originais, o resultado é Ana = 1100, Bruno = 500, Carla = 750. As operações anteriores ao ponto ainda precisam de COMMIT.

Experimento: duas conexões

Restaure os saldos. Execute A1, B1, A2, B2 e B3 na ordem indicada. Use conexões independentes.

Sessão A

-- A1
USE laboratorio_transacoes;
START TRANSACTION;
UPDATE contas SET saldo = 1200
WHERE id = 1;
-- A2 (após B1)
COMMIT;

Sessão B

-- B1 (após A1)
USE laboratorio_transacoes;
SET SESSION TRANSACTION ISOLATION LEVEL
    READ COMMITTED;
START TRANSACTION;
SELECT saldo FROM contas WHERE id = 1;
-- B2 (após A2)
SELECT saldo FROM contas WHERE id = 1;
-- B3
COMMIT;

Em READ COMMITTED, B lê 1000 e depois 1200. Repita com REPEATABLE READ (restaure antes): B lê 1000 nas duas consultas.

Modelo didático de leituras SELECT simples em transações explícitas. SERIALIZABLE aguarda o bloqueio de A; o simulador permite A confirmar enquanto B espera.

Sessão A — execute primeiro

USE laboratorio_transacoes;

WHERE id = 1 FOR UPDATE;
UPDATE contas SET saldo = saldo + 100
WHERE id = 1;
-- Após iniciar B, execute:
COMMIT;

Sessão B — enquanto A está aberta

USE laboratorio_transacoes;
START TRANSACTION;
UPDATE contas SET saldo = saldo + 50
WHERE id = 1;
-- Aguarda A liberar o bloqueio.
COMMIT;

Se ambas confirmarem antes do timeout, Ana terá R$ 1.150 (partindo de R$ 1.000). Bloqueios são liberados no encerramento da transação.

Transferência com validação

Execute os comandos separadamente e inspecione os resultados. Bloqueie contas em ordem consistente para reduzir deadlocks.

START TRANSACTION;
SELECT id, saldo FROM contas
WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
-- Verifique: duas contas distintas existem.
UPDATE contas SET saldo = saldo - 200
WHERE id = 1 AND saldo >= 200;
SELECT ROW_COUNT() AS debitadas;
-- Continue SOMENTE se debitadas = 1.
UPDATE contas SET saldo = saldo + 200 WHERE id = 2;
SELECT ROW_COUNT() AS creditadas;
-- COMMIT somente se creditadas = 1 e sem erros.
-- Caso contrário: ROLLBACK;
Sucesso → COMMIT;Falha → ROLLBACK;

Em produção, a aplicação ou uma procedure deve implementar essas condições, tratar exceções e repetir transações vítimas de deadlock quando apropriado. Não execute o bloco inteiro cegamente.

Autocommit na prática

SELECT @@autocommit;
SET autocommit = 0;
UPDATE contas SET saldo = saldo + 10 WHERE id = 1;
ROLLBACK;
SET autocommit = 1;

Ao mudar autocommit de 0 para 1, uma transação pendente é confirmada; encerre-a antes. Prefira START TRANSACTION para delimitar operações explicitamente.

Teste de falha de uma instrução

START TRANSACTION;
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;
-- Execute separadamente: deve violar CHECK.
UPDATE contas SET saldo = -1 WHERE id = 1;
-- Após o erro, verifique o saldo de Bruno nesta sessão:
SELECT * FROM contas WHERE id = 2;
ROLLBACK;

O primeiro UPDATE continua pendente mesmo após o erro de CHECK no segundo. Execute ROLLBACK explicitamente.
